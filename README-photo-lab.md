# Couple photo lab

The real version of the AI couple photos flow: one photo of a couple goes in,
five pictures of the two of them in five places come back, generated by Gemini
for real. Everything that matters is editable in the page, so a prompt or a
model can be changed and retried without touching any code.

## Where it runs

| Where | Address |
|---|---|
| Local | `/lab` |
| Its own subdomain | any host containing `photo-lab`, where the lab is `/` |
| Local, as if on that subdomain | `VITE_APP_VARIANT=lab npm run dev` |

It sits outside the phone frame and outside the app shell, because it is a
desktop testing tool rather than a screen for a customer. Nothing about the
main prototype changes.

```bash
npm run dev
```

Then open `http://localhost:5201/lab` (or whichever port Vite prints).

## What it does

1. **Gemini key.** Typed in, kept in this browser only, sent to Google alone.
   "Load models from key" asks the API which models the key can actually use and
   puts them in the two dropdowns, so nothing depends on a hardcoded list going
   stale. Any model id can also be typed by hand.
2. **The couple photo.** Dropped or picked. It is shrunk to 2048px on the long
   edge, then sent straight to the small model with the check prompt. The verdict
   comes back as a code, and the lab shows both the code and the line the couple
   would actually be shown. A rejected photo can still be used for testing with
   "use it anyway".
3. **The subject read.** Before any generation, the small model is asked who these
   two people are. It returns a written description of each face and a box around
   each head, and the lab crops those heads out. Both ride along with every
   request: the words go into the prompt at `{People}`, the crops go in as extra
   reference pictures. A single full-body reference at 1024px leaves a face about
   100px across, which is not enough to copy, and this is the fix for that.
4. **The places.** Thirty preset locations across Bali, Maldives, Mauritius, New
   Zealand, Thailand and Vietnam, each with its own scene photo. Pick up to five,
   or hit "Pick 5" for a random set. "Add place" takes a name, a country and a
   photo, and the new place is stored in the browser and sits alongside the
   presets.
5. **The workflow.** Nine different ways of making the picture, picked from a
   card. They differ in how many calls they make and what goes into each one, and
   the whole point of the lab is finding which one holds a likeness best. See
   "The nine workflows" below.
6. **The batch.** One request per place goes out at the same moment, or several
   for the workflows that work in steps. Each carries the prompt with that place's
   name substituted in, the place's photo as IMAGE 1, the couple's photo as
   IMAGE 2, the face crops after it, and a line binding the left person to the
   left and the right to the right. By default every result is held back until
   they have all landed, so the set arrives together.
7. **The likeness agent.** Each result is shown to the small model next to the
   original photo and scored out of 100 on one question only: is this the same two
   people. Anything under the target goes again, carrying the judge's corrections
   ("the jaw is narrower", "the beard has been trimmed"). The best scoring attempt
   is what you get, not the last one. Two attempts by default, and the score plus
   whatever is still wrong sits on every tile.
8. **Results.** A tile per place with the time it took and the payload size,
   click for full screen, arrow keys to move between them, save one or save all.
   Anything that failed shows the message Gemini returned and can be retried on
   its own without rerunning the other four.

## The nine workflows

All nine end the same way, with a picture and a score, so they can be compared
directly. What differs is the route.

| # | Workflow | Calls | What it does differently |
|---|---|---|---|
| 1 | One shot | 1 per attempt | The location photo as it is, plus the couple photo and face crops. The location's own couple acts as a pose template, until the photos are rebuilt without people. |
| 2 | One person at a time | 2 per attempt | Places one person, then the other into that result. One face per call. |
| 3 | Empty scene first | 1 per attempt | The location with its own people removed first, so the couple's photo is the only face in the request. |
| 4 | Empty scene, more photos | 1 per attempt | As above, with two to four photos of the couple attached. Needs at least one extra upload. |
| 5 | Describe first, strict judge | 2 per attempt | Reads the couple into words and the scene into notes, composes from those, then a pass or fail gate with one correction per retry. |
| 6 | Fix the faces after | 1 per attempt, plus 2 | Makes the picture, then a second call replaces only the two faces. |
| 7 | Cut out and blend | 1, plus 1 per attempt | Cuts the couple out onto white, pastes them into the empty scene in the browser, then one call only relights and reclothes. Faces are never regenerated. |
| 8 | Close up, then place | 1, plus 1 per attempt | Generates a large close up of the couple in holiday clothes, shrinks and pastes it, then blends. Big faces copy better. |
| 9 | Everything on | 2 per attempt | Empty scene, every reference photo, the written description and the strict gate together. |

**What each one needs.** Workflows 3 to 9 want the scene emptied, and 5, 7, 8 and
9 also want it read. Both are built on the first run that needs them and kept for
the runs after. Emptied scenes are held in memory and lost on reload; scene notes
are small JSON and are kept in the browser, and can be edited by hand in "Scene
setup" when the model puts the couple in the wrong spot or at the wrong size.

**Workflows 7 and 8 do their compositing in the browser**, with a chroma key on
the flat white background, a trim to the content, and a scale and paste at the
percentages in the scene notes. The paste is deliberately crude. The Gemini call
after it is told to leave the faces alone and fix everything else, which is the
whole bet: if that call repaints the faces anyway, the judge will show it.

## Pose, size and spot

There are two generation prompts, because they are two different jobs.

A location photo that still has its own couple in it **is** a template: it hands
over the standing spot, the scale, the foreshortening and the pose for free, and
none of those four then have to be reasoned about. That is what the first prompt
uses, and it is why workflows 1 and 2 lean on it.

Take those people out and the template goes with them. Worse, the instruction now
points at nobody, and telling a model to replace people who are not in the picture
is how you get a mess. So an emptied scene gets its own prompt: the same insistence
on the faces, no template to copy, and the choice of spot handed over. Workflows 3
and up use it, and workflows 1 and 2 switch to it the moment the source photos have
been rebuilt.

**How much freedom the model gets** is one setting, and it only applies where the
scene has nobody in it:

| Setting | What goes in the prompt |
|---|---|
| The model chooses, freely (default) | Pick the spot a real couple would stand for a photo here. Pose to suit the place and each other. Size so the perspective is honest, big enough to recognise a face, small enough that the place is still the subject. Feet on the ground, view unblocked. |
| The scene notes suggest | The spot and height read off the photo, said as a reading rather than an instruction, with the model told to use its own judgement if the scene suggests better. |
| Pinned to the scene notes | The spot and the exact height, no more and no less. |

Anything other than free needs the scene read, so that read now happens for any
workflow whose scene has been emptied, not just the four that want it for the
outfit. The prompt carries a `{Framing}` token where that block lands; a prompt
edited so the token is lost gets the block appended instead, and says so.

Workflows 7 and 8 are the exception. They paste a real cutout onto a real
background in the browser, and a paste needs actual numbers, so those two always
use the spot and height from the scene notes whatever this is set to. That is also
why those numbers are editable by hand.

## Racing them against each other

"Race several on one place" turns the batch into a comparison. Every ticked
workflow runs on the first picked place, three at a time so a key does not collect
rate limits, and then **one judge scores all of them with the same prompt**. That
last part matters: workflow 5's strict gate and the likeness agent do not score
alike, so neither can crown a winner. The uniform score is what the badge shows in
a race, and the best one gets a Winner mark. Costs one extra judging call per
workflow, and the run button says roughly what the whole race will cost before it
is pressed.

## Keeping the likeness

This is the hard part of the whole thing, and it is where most of the settings are.

**Placing one person at a time** is workflow 2, and it is the default. Two people
in one request means the model has four faces in front of it, two from the couple
and two from the location photo, and it averages them. Instead, the couple's photo
is split: one call places the first person with only their own face crop attached,
then a second call places the other into that result while being told the first is
already correct and must not be touched. Each call has exactly one face to copy, so
there is nothing to blend with. Tiles from a two-pass run offer "See the first
pass", which is worth a look when a result goes wrong, because it tells you which
of the two passes broke it.

**Send images at** does not apply to the couple's photo, which always goes at full
size. Starving the model of face pixels to save a second is a bad trade.

**Send the couple before the location** swaps the order of the two pictures.
Whichever goes first tends to dominate. Scene first keeps the place faithful,
people first holds the faces better. Worth testing both ways on the same photo.

**Temperature** defaults to 0.35. This is a copying job, not a creative one.

**Emptying the scene** takes the existing couple out of a location photo and keeps
the result, so the model has no other faces in front of it to borrow a jaw or a
beard from. One call per place, reused for every couple after that. Every workflow
from 3 up does this, and the tile says when an emptied scene was used.

**Never regenerating the face at all** is workflows 7 and 8, and it is the only
approach here where the likeness cannot drift by construction. The cost moves to
edge quality and lighting, which are easier to judge by eye than a face that is
subtly the wrong shape.

## What is configurable

Every prompt is a plain text area, read fresh on every request. The first two live
in their own panels; the eight the newer workflows use are behind "Advanced
prompts", one drawer each, so the rail is not ten permanent text boxes.

| Prompt | Used by |
|---|---|
| Check | every run, on upload |
| Subject read | every run, for the face crops and the `{People}` words |
| Generation, scenes with people | workflows 1 and 2, while the photos still have people in them |
| Generation, empty scenes | workflows 3, 4 and 6, and 1 and 2 after a rebuild |
| Likeness | the agent loop, and the judge that scores a race |
| Descriptor read | workflows 5 and 9 |
| Scene read | workflows 5, 7, 8 and 9, once per place |
| Composite | workflows 5 and 9 |
| Strict gate | workflows 5 and 9 |
| Face swap | workflow 6 |
| Cut out | workflow 7 |
| Blend | workflows 7 and 8 |
| Close up | workflow 8 |

The tokens, all optional and all substituted at send time:

| Token | Becomes |
|---|---|
| `{Location name}` | the place, for example `Ubud` |
| `{Country}` | the country the place sits in |
| `{People}` | the subject read, or the descriptor read where a workflow has one |
| `{Outfit}` | the outfit from that place's scene notes |
| `{Height}` | how tall the couple should stand, as a percentage of frame height |
| `{Placement}` | where and how they stand |
| `{Light}` | the light read off the scene's own shadows |
| `{Framing}` | the whole pose, size and spot instruction, which changes with the setting above |

A generation prompt edited so that `{People}` is lost does not silently throw the
description away: it is appended as its own block instead, and the panel says so.

Alongside them: model, temperature, image size, aspect ratio, whether the
pictures are labelled `IMAGE 1:` and `IMAGE 2:` in the request, whether a line is
appended asking for one frame, whether the five are revealed together, and what
size the images are sent at. Every setting is remembered across reloads, and each
prompt has its own Reset.

**Aspect ratio defaults to "Match the location photo"**, which reads each scene's
real dimensions and asks for the accepted shape closest to it. Leaving it on Auto
hands the choice of canvas to the model, and a 3:4 portrait scene can come back
on a 16:9 canvas with the spare width filled by a second panel, so the result is
a before and after diptych rather than one photo. Every tile says which ratio was
actually asked for.

Two settings exist for the same failure. The `IMAGE 1:` and `IMAGE 2:` labels are
**off** by default, because labelled inputs push the model towards a labelled
comparison sheet. The one frame line is **on** by default, and is appended at
send time rather than written into the prompt, so the prompt in the panel stays
exactly what was typed.

**Send images at** is the one to reach for when testing feels slow. The whole
batch is five uploads, so 2048px is the slowest and most faithful, 1568px is the
default balance, and 1024px is for quick prompt iteration.

Model support for `responseModalities` and `imageConfig` varies between ids. Any
field a model rejects is dropped and the call retried, and the tile says which
field was dropped, so an unsupported size or ratio never fails the batch.

## What survives a reload

Settings live in localStorage, which is right for a few kilobytes of text and
wrong for pictures: its quota is about five megabytes and one generated photo can
be two. So the pictures and the results go in IndexedDB instead, which is measured
in hundreds of megabytes and holds blobs directly rather than as base64 a third
larger than the bytes it carries.

Kept between reloads, and across a preview restart:

| Kept | Where |
|---|---|
| The couple photo, at the size that gets sent | IndexedDB, as a blob |
| Extra reference photos | IndexedDB, as blobs |
| Emptied scenes | IndexedDB, as blobs |
| Every generated result, and its rough or first pass | IndexedDB, as blobs |
| The results themselves: scores, timings, corrections, which workflow | one JSON snapshot |
| The subject read and the longer read, including the face crops | the same snapshot |
| Scene notes, every prompt, the model list, all the settings | localStorage |

**A result is written the moment it lands**, not at the end of the batch, so a
preview that stops halfway still keeps whatever came back before it did. Anything
that was still running when the page went down comes back marked stopped rather
than spinning for ever.

The snapshot holds no image bytes of its own, only a flag saying which pictures
exist, and anything it stops pointing at is deleted on the next save. "Start
fresh" empties both stores. The lab also asks the browser to treat the origin as
persistent, so the data is not evicted when disk gets tight.

## Rebuilding the location photos

The preset photos each have their own couple standing in them, which is useful as
a pose and scale template and unhelpful as a second pair of faces. "Scene setup"
has a one-off tool that runs all thirty through the image model, asks for the same
photograph with the people removed and everything else untouched, and writes each
result over the original file.

Writing to disk needs a server, so there is a dev-only endpoint at `/lab-write`
registered by a plugin in `vite.config.js`. It is deliberately narrow: it writes
only into `public/lab-locations`, only accepts a slug ending in `.jpg`, and copies
whatever it is about to overwrite into `public/lab-locations/with-people/` first,
so every original is recoverable. It does not exist in a production build.

**What the first real sweep taught us**, all now handled:

- Writing a file wakes the dev server's watcher, and this project force reloads the
  page on any change, which killed the sweep after the first photo. The thirty
  writes now go in one request, so the only reload lands after the last file, and
  `server.watch.ignored` covers the folder as well.
- A missing path under `public/` is answered with the app's own `index.html`, not a
  404, so a plain "does the backup exist" check said yes for all thirty and fed
  HTML to the model. The check now insists on an image content type.
- Ask for the largest size the model offers, then redraw to the original's exact
  pixels. Left alone, one came back 768px on the long edge, and the location photos
  are the source material for everything else.
- Seven of the thirty originals are stored sideways with an EXIF rotation flag.
  Browsers always displayed them upright, which is what the lab saw, so the rebuilt
  files are stored upright with no flag. Same shape on screen, one less thing to
  misread.
- **Two of thirty needed a second go.** One came back untouched, and one had the
  person removed but their shoes left standing on the path. Neither is an error the
  code can catch, because an image did come back. Look at the grid after a sweep,
  and for anything wrong, drop it from the done list and run again. A second
  attempt fixed both.

After a rebuild, turn on **"the location photos already have nobody in them"**.
Every workflow that wanted the scene emptied then skips that call and uses the
photo as it is, which is one call less per place, and workflows 1 and 2 switch to
the empty scene prompt. What the old photos were giving away for free was the pose,
the scale and the standing spot; those now come from the setting above instead.

## How the calls are made

Straight from the browser. In dev they go through a Vite proxy at `/gemini-api`
so CORS never comes up; anywhere else they go directly to
`generativelanguage.googleapis.com`. There is no backend and no server-side key.

That is fine for local testing and wrong for anything public: the key is visible
to anyone with the page open. Real deployment needs the key held server side.

## The images

`public/lab-locations` holds the thirty scene photos, downscaled to 2048px on the
long edge from the originals. `src/data/labLocations.js` lists them. To swap the
set, drop new files in and update that list; the names in it are what the prompt
sees.

## Not built

No backend, no auth, no rate limiting, no cost tracking, and no moderation beyond
whatever the check prompt catches. Nothing is shared between browsers: a session
is kept on the machine that made it.

Three approaches worth knowing about are out of reach here, because all three need
a server with a GPU rather than a browser:

- **A dedicated face swap model** (InSwapper, ReActor, FaceFusion) is what most
  consumer apps doing this actually use, and it is far better at identity than any
  general image model. Workflow 6 is the same idea done with Gemini, which is
  weaker. Some of those models also have licence terms that need a look before
  commercial use.
- **A small adapter trained per couple** (a LoRA on five to fifteen photos) is the
  highest fidelity option available anywhere, at a few minutes of GPU per couple.
  Plausible as a premium tier later, not as a default.
- **Masked inpainting**, where a mask says which pixels may change, would keep the
  background pixel identical and raise the effective face resolution. The Gemini
  API takes no mask, so workflows 7 and 8 approximate it by compositing in the
  browser first.

**Comparing models** is a smaller gap and the compare mode is most of the way
there: the same race, keyed by model id instead of workflow, would turn the choice
of image model into a number instead of an argument. Not wired up yet.
